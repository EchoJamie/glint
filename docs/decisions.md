## 1. 项目目标与使用背景

第一目标是开发者自己在 Mac 上长期使用；第二目标是公开放到 GitHub，允许其他人获取、使用、修改和分享。没有商业化计划，也不额外设置个人、组织或商业用途限制。

原有使用方式以系统简体拼音和 ABC-Extended 为主，中文使用全拼。最初希望保留这套输入方式；2026-09-18 用户进一步反馈，使用 Caps Lock（大写锁定键）切换输入方式时，无法保证保留尚未上屏的原始拼音字符，例如 `nihao`，因此不再坚持使用 ABC-Extended。

当前以切换过程中的文本连续性为体验要求：保留全拼习惯，英文输入方式允许调整。上述反馈是用户观察到的使用问题，尚未定位到系统切换、客户端或配置中的具体原因。

用户随后明确：当前鼠须管已经实现“原始拼音上屏 + 中英文切换”，这套体验可以接受；暂时没有大写锁定功能也可以接受。希望新项目探索长按 Caps Lock 开启大写锁定，作为可选增强。

最初的问题是候选词、常用词和专业词：一段时间常用的词较容易出现，间隔一段时间再使用时可能难以找到。用户不能确定具体原因是缺词、排序下降还是候选不可见，因此不能直接断言词条被删除。

用户随后安装鼠须管，使用约一周后明确反馈：候选词体验有所提高，Rime 引擎可以接受。当前主要不满意的部分转向配置管理、界面样式和候选浏览。

卷轴选词的核心诉求是一次看到更多候选，并能够连续浏览，减少每次只能看到几个词、反复翻页寻找的操作。

2026-09-20 用户明确，“卷轴”指的就是 Mac 原生输入法的候选体验。结合既有简体全拼使用背景，后续以用户本机 macOS 原生简体拼音候选窗为交互参照，无需重新让用户在抽象的横排、竖排或网格方案间选择。

同日用户补充：输入法必须支持 Mac 的 Touch Bar（触控栏），体验沿用原生方式。将其纳入正式功能需求，与屏幕候选共同使用 Rime 的候选与选择逻辑；是否有触控栏不改变普通键盘和屏幕选词能力。

用户进一步指出，鼠须管通过直接编辑配置文件调整设置的方式，缺少期望中的完整界面交互。新项目需要将可视化设置和管理作为核心产品能力，使日常调整可以通过界面完成。这是对使用体验的要求，不据此将鼠须管或 Rime 的工程成熟度判定为验证项目。

用户还提出个人词库、专业词库导入导出的入口缺失，以及长拼音分词解析、自动纠错偶有问题。用户随后明确，“前置单字 + 后续名词”的分词问题出现概率很低，仅记录、暂不处理。用户询问过双拼，但尚未决定更换全拼。此前认可候选体验改善，不等于已经验收全部长句输入行为。

## 3. 架构职责边界

以下是后续设计的职责基线，不代表已确定具体类、文件、线程或进程结构。

| 部分 | 职责与处理方向 |
| --- | --- |
| Rime 与输入方案 | 拼音解析、分段组句、候选生成与排序、选词、自动学习和用户词库。 |
| macOS 系统接入 | 按键与修饰键处理、输入会话和焦点、中英文模式切换、预编辑文本及切换时的处理、上屏、输入位置与应用兼容。参考鼠须管的成熟实现，按许可决定复用范围。 |
| 候选界面 | 以 macOS 原生简体拼音候选窗为交互参照，实现候选排布、展开收起、连续滚动、鼠标和键盘导航、选词反馈、窗口样式与定位。 |
| Touch Bar 接入 | 通过系统文本输入机制提供原生风格候选条，与屏幕窗口共享候选身份、选中项和引擎确认链路；遵守宿主应用及系统的触控栏显隐设置。 |
| 配置管理界面 | 提供面向日常使用的可视化设置，说明选项含义，反馈实际生效结果。底层优先复用现有配置与部署机制；具体页面和选项范围尚未确认。 |
| 数据管理 | 保留并维护 Rime 学习数据，处理必要的迁移、备份与恢复，不额外建设重复词频系统。云同步只搬运 Rime 已有的快照与配置文本，不另建一套词频或配置存储。 |

候选界面的实现约束：

- 展示使用引擎返回的候选及顺序，不另行建立候选排序或学习逻辑。
- 鼠标点击、数字选词和键盘确认使用一致的当前候选索引映射。
- 修改输入、移动组合光标、改变分段或切换会话后，使过期候选缓存失效。
- 通过 Rime 执行候选选择，再处理其提交结果；不能由 UI 直接插入候选文字，绕过组句与学习。
- 候选选择可能只完成部分拼音的转换，界面必须继续反映剩余组合状态。

候选交互已形成[完整功能方案](native-candidate-interaction.md)：默认紧凑横排，下方向键或按钮展开为多行连续卷轴，Escape 先收起；编号、键盘和鼠标统一映射到 Rime 全局候选索引，修改输入后刷新，部分选词后继续组句。资料明确的原生能力与本项目对细节的设计约定分别说明，不再等待用户重新选择排布方向。尚未完成原生窗口实机核对或新产品实现验收。

窗口实现先验证公开 InputMethodKit 候选组件是否满足增量滚动、候选身份、按键路由和样式等要求；不满足时仅将候选视图替换为 AppKit 非激活窗口与滚动视图。最终保留一种实现，不建设多渲染器框架。公开组件的存在不等于现代系统拼音的全部体验均可直接复用。

Touch Bar 同时纳入上述选型验证。AppKit 的公开候选条能够接收文本输入系统候选，但不能由此推断在输入法进程创建普通 NSTouchBar 就能控制其他应用的触控栏。先验证 InputMethodKit 与宿主输入上下文之间的显示及选择回调；若屏幕候选采用自研 AppKit 视图，也必须保留已验证的系统触控栏接入。具体规则见[Touch Bar 功能与接入方案](native-candidate-interaction.md#41-touch-bar触控栏功能规则)。

鼠须管主要提供 Mac 系统接入和 Rime 集成参考；Fcitx5 macOS 提供卷轴及候选适配的实现参考，目标交互以 macOS 原生简体拼音为准。是否直接复用 `fcitx5-webview` 尚未确定，也没有决定引入完整 Fcitx5 框架。

中英文切换的体验基线：

- 典型场景：全拼模式下输入 `nihao`，尚未确认候选，此时切换到英文输入。
- 已确认要求：将原始字母 `nihao` 原样上屏，随后进入英文模式；不能丢失文本、重复提交或意外提交候选汉字。用户反馈鼠须管目前已经达成这一体验，不再将“保留在组合缓冲区”列为该场景的待选方案。
- 可选增强：短按 Caps Lock 保持中英文切换，长按开启大写锁定。用户接受暂时没有大写锁定，因此不能为此牺牲现有切换体验或阻塞首版使用。
- 待设计事项：长按的识别方式与时长、关闭大写锁定的操作、长按是否同时切换英文，以及切回中文或已有部分汉字确认时的文本处理规则。
- 优先沿用现有 Rime 模式与配置。参考版本的 `ascii_composer` 已有 `commit_code` 切换分支，但尚未核对用户当前生效配置，也未验证混合组合等边界；不能把示例中的纯拼音行为直接推广到所有组合状态。不预先增加第二套组合缓冲区。[参考实现](https://github.com/rime/librime/blob/33e78140250125871856cdc5b42ddc6a5fcd3cd4/src/rime/gear/ascii_composer.cc#L243)

长按大写锁定的初步可行性记录（仅文档与源码核对，未做实机验证）：

- macOS 自带输入源切换设置已有按住 Caps Lock 开启连续大写输入的交互，说明这一操作有系统先例；它涉及系统输入源切换，不能据此认定输入法内部中英文模式切换可直接复用。[Apple 输入源设置说明](https://support.apple.com/en-sg/guide/mac-help/-mchl84525d76/mac)
- Apple 文档通过 `flagsChanged` 检测 Caps Lock 状态；参考鼠须管也在该事件中依据锁定标志变化处理切换。现有路径不能直接证明能够取得完整的物理按下与松开时刻，因此不能只加一个普通按键计时器就承诺长按可靠可用。[Apple 事件说明](https://developer.apple.com/library/archive/qa/qa1519/_index.html)、[鼠须管参考实现](https://github.com/rime/squirrel/blob/0cd71a6130a5866b0ae6ba0494929ebdc8211194/sources/SquirrelInputController.swift#L54)
- 后续以小型原型验证当前 Mac 与实际使用键盘上的事件、模式及锁定状态同步，确认长按不会误触发短按切换。尚未决定引入全局键盘监听或额外常驻组件。

### 3.1 设置与管理的产品方向

本轮收敛的要求是让日常设置具备完整的图形交互。以下保留产品方向；2026-09-20 已在[实施计划](implementation-plan.md#6-设置与词库任务的落地范围)给出首版建议清单及阶段安排，具体页面仍需设计，不把执行建议视为用户逐项确认。

| 使用任务 | 建议的界面能力 |
| --- | --- |
| 调整输入习惯 | 中英文切换、按键行为和常用标点选项；用具体输入示例解释效果。 |
| 调整候选窗口 | 字体、字号、外观和卷轴相关设置；提供与实际候选窗口一致的效果预览。 |
| 管理方案与词库 | 查看当前使用组合，提供个人词库与专业词库的导入导出、启用及学习数据备份恢复入口；2026-09-24 补入 iCloud 同步开关及其进度、冲突与失败反馈。具体格式、页面和首版范围待定，不要求用户逐个录入常用词。 |
| 确认修改结果 | 明确显示正在应用、已生效或失败；失败时给出可执行的处理方式，并保留可用配置。 |

设计与实现原则：

- 以“用户想完成什么”为页面组织依据，给常用功能合理默认值；不将全部配置键机械转换成表单，也不要求用户先掌握 YAML、补丁或部署概念。
- 可视化界面负责配置的读取、修改和应用，Rime 相关选项继续使用其已有配置与部署机制，外壳专属选项由外壳管理。同一选项避免维护两套独立的持久化状态。
- 效果预览和实际生效状态分别表达；不能仅凭文件写入成功就显示已生效。如何安全应用变更、何时避免打断正在输入的文本，留待技术设计验证。
- 高级配置文件入口可作为补充。界面只修改其负责的选项，保留其他自定义内容；高级编辑与界面如何协调，仍需确定规则。
- 不将“完整交互”扩展为通用 Rime 配置编辑器、主题市场或插件平台。先覆盖本项目已确认的日常使用场景。

### 3.2 iCloud 同步

2026-09-24 新增需求：提供可开启的 iCloud 同步，默认关闭。覆盖个人学习词典与用户配置，两者机制不同，分先后实施。以下技术路径已核对参考源码与官方说明，尚未实测。

接入方式：输入法不能沙盒化，因此可以把 `~/Library/Mobile Documents/com~apple~CloudDocs` 当普通文件夹直接读写，无需 iCloud entitlement；代价是拿不到正式的 ubiquity container，也不使用 CloudKit，同步只能靠文件搬运。[开发者论坛的实测说明](https://developer.apple.com/forums/thread/727902)、[entitlement 的分发限制](https://developer.apple.com/forums/thread/18443)

本机实况（2026-09-24 只读检查）：iCloud Drive 目录存在；`~/Library/Rime/installation.yaml` 已有 `installation_id`，未设置 `sync_dir`；尚无 `sync/` 目录，即此前从未同步过；用户词典为 `rime_ice.userdb`，名称取自**词典** `rime_ice`（雾凇拼音），不是方案名。iCloud Drive 内未发现未下载的 `.icloud` 占位文件，但该情况仍需在实现中处理。

| 数据 | 同步方式 | 冲突语义 |
| --- | --- | --- |
| 个人学习词典 | 复用 Rime 的 installation 快照交换：快照是纯文本 `<词典名>.userdb.txt`，按 `installation_id` 分目录；每次同步先把可见的所有 installation 快照合并进本机库，再导出本机快照 | 字段级单调合并（`tick` 取最大、`commits` 取绝对值较大者、`dee` 取最大），双向收敛，不让用户逐条选择 |
| 用户配置 | 文件搬运。不能直接让 Rime 的同步任务把 `sync_dir` 指向云盘，该任务会连带按 `*.yaml` 复制配置，且写入不是原子的 | YAML 文本**没有合并语义**。需维护上次同步后的哈希基线：只有一侧改动则取改动方；两侧都改过则判为冲突，不自动覆盖，交由用户处理。写入前备份，写入后触发部署，部署失败回滚到上一套可用配置 |

**必须排除**：`.userdb` 数据库目录（LevelDB，云盘逐文件同步会造成内部文件不一致；librime 打不开用户库时会尝试修复，修复失败则把库改名 `.old` 并重建为空库）、`installation.yaml`（含 `installation_id`，两台机器共用会导致快照互相覆盖）、`user.yaml`（理由见下）、`build/` 编译产物、`sync/` 目录自身。Rime 自带的配置备份只遍历用户目录顶层、按扩展名挑 `.yaml`/`.txt`，会跳过带 `customization` 键的自动生成补丁文件，但**不会**跳过 `installation.yaml`，必须由外壳显式排除。

`user.yaml` 整文件排除，不做字段级同步。它混合了两类内容：本机运行状态与用户偏好。librime 只往其中写四类字段——`var/last_build_time`（上次部署时间戳，`deployment_tasks.cc:252`）、`var/previously_selected_schema` 与 `var/schema_access_time/*`（选中方案及访问时间，`switcher.cc:167-168`）、`var/option/*`（被 `save_options` 列出的开关）。其中 `last_build_time` **绝不能同步**：librime 拿它和当前时间比较来决定是否需要重新部署（`deployment_tasks.cc:72-73`），从另一台带来一个更晚的时间戳会让本机**跳过部署、配置改了却不生效**。整文件搬运必然连它一起带过去，因此不采用。方案选择不同步的代价很小（切换一次即持久），开关类偏好更适合用 `*.custom.yaml` 固化，那属于配置同步范围。若日后确有需要，只做 `previously_selected_schema` 单字段同步，不整文件搬运。

快照写入不是原子的（直接截断写目标路径，无临时文件、无 fsync），而读取时遇到解析失败的行只记警告后跳过。因此快照在云盘上被截断会**静默丢词条**。外壳负责搬运时须用临时文件加原子改名写入，并在合并后核对条目数。

**触发时机**：定时同步，默认间隔 **6 小时**；另加两个兜底触发——**启动时**同步一次，以及设置页内的「**立即同步**」按钮。间隔在设置中可调，也可关闭定时。选 6 小时是因为词典类数据的滞后感知很弱，几小时的延迟不影响使用，而更短的间隔只会增加云盘写入噪声和冲突窗口（iCloud 自身的文件传播还有几秒到几十秒延迟，跑得比它快没有意义）。同步只使用输入法进程内的定时器——输入法本身常驻，不为此新增后台进程或常驻服务。定时到了但用户正在输入组合、或正在部署时，延后到空闲再执行；睡眠期间不补跑。

**开关语义**：关闭时不删除云端文件，也不删除本机数据；重新开启后继续合并。同步失败（无 iCloud 账号、目录不可用、快照解析失败）须明确反馈，本机输入不受影响，不静默降级；解析失败的行必须报出，不能当作同步成功。失败不弹窗打断输入，改为写入诊断记录，并在设置页显示最近一次同步的状态。

## 4. 长期词汇记忆的处理原则

长期自动记词仍是最初目标的一部分，但用户已经认可当前 Rime 的使用体验，因此现阶段不预先改造学习算法。

后续如出现实际问题，分别核对：

1. **自动学会**：通过正常输入和选词，目标词是否形成了学习记录。
2. **长期找回**：大量使用其他词之后，完整拼音是否仍能检索到旧词。
3. **排序恢复**：旧词重新选用后，候选排名是否合理回升。

词库中存在、能被检索返回、排在可见候选中，是不同的事实。不能只依据数据库持久化或短期主观体验，宣称已经实现永久可找回。

只有确认现有方案或引擎机制无法满足需求时，才考虑调整对应配置或实现。优先解决已定位的约束，不默认新增长期词库、回灌服务或 UI 补词逻辑。

### 4.1 个人词库与专业词库管理

已核实 Rime 提供用户词典快照备份、合并恢复，以及文本码表导入导出；参考 librime 源码的 `rime_dict_manager` 也包含对应命令。官方说明指出鼠须管缺少该功能的图形工具，不能将入口缺失等同于引擎不支持。[Rime 用户词典管理说明](https://github.com/rime/home/wiki/UserGuide#用戶詞典管理)、[参考工具源码](https://github.com/rime/librime/blob/33e78140250125871856cdc5b42ddc6a5fcd3cd4/tools/rime_dict_manager.cc)

产品设计需要区分以下用途。2026-09-20 的[实施计划](implementation-plan.md#62-词库交换与迁移)建议首版优先支持 Rime 原生快照、原生用户词典文本与兼容的扩展词典；实际格式以实施时锁定的工具版本验证，具体页面尚未设计：

| 用途 | 处理方向 |
| --- | --- |
| 迁移个人学习习惯 | 优先复用用户词典快照及合并恢复机制；普通文本导出不包含快照的全部信息，不能宣称二者完全等价。 |
| 批量交换个人词条 | 提供可读文本的导入导出，显示目标词典、有效条目及处理结果；词条编码必须与目标方案的词典兼容。 |
| 安装与分享专业词库 | 优先作为独立扩展词典管理，提供导入、启用和导出入口；不默认把整个专业词库灌入个人学习记录。支持格式、冲突处理及来源信息待设计。 |

后台优先复用 Rime 的现有机制，并处理运行中数据库的占用与一致性；不让用户手工关闭进程或逐词维护来完成日常管理，也不预先承诺兼容所有第三方词库格式。本轮未执行实际导入导出，未读取个人学习词条。

### 4.2 长拼音分词、纠错与双拼的边界

当前处置（2026-09-18）：用户明确“前置单字 + 后续名词”的问题为低频现象，仅记录、暂不处理。不纳入当前排查、修复和首版验收要求，也不继续要求用户提供例句。以下分析保留供追溯，后续是否重启由用户另行决定。

“分词不对”需要通过实际输入样例区分，以下例子仅用于说明问题类别，并非用户问题的复现：

| 问题 | 示例或表现 | 双拼可能带来的变化 |
| --- | --- | --- |
| 拼音音节切分 | `xian` 对应一个音节，或希望表达 `xi an` | 完整双拼编码通常以两键表示一个音节，边界更规则，可能减少这类歧义；简拼混输和误按键仍可能引入其他问题。 |
| 词句组合与候选排序 | 音节正确，却选择了不合语境的词，例如“权利/权力” | 仍依赖词库、用户学习及组句策略，更换编码方式不能直接解决。 |
| 拼写纠错 | 漏键、多键、相邻字母交换等 | 双拼减少部分按键，但仍会误输入；纠错能力需要按具体方案验证，不能承诺切换后更强。 |

用户补充的问题模式（2026-09-18）：暂时无法回忆完整例句，但记得输入开头是一个起衔接作用的单字，后面的第二、第三个字才组成名词，连续输入时出现不符合预期的解析。单字的具体词性尚未确定，不直接归类为量词。

此前的工作假设（现仅留档）：可能涉及“前置单字 + 后续名词”的词语边界与组句选择，也可能涉及跨音节切分、纠错或词库覆盖，尚未定位根因。“在 / 项目 / 中”“把 / 文件 / 打开”等结构仅为说明，不是用户的原始错误样例。

此前提出的单独输入、连续输入与分段确认对照思路仅作为历史分析保留，当前不安排复现或测试。该问题不阻塞已确认的界面和管理设计。

Rime 的双拼方案可通过编码映射对接拼音词典，因此输入编码与词句选择能力应分别评价。[Rime 双拼说明](https://github.com/rime/home/wiki/UserGuide#雙拼)、[拼写运算说明](https://github.com/rime/home/wiki/SpellingAlgebra)

2026-09-18 只读查看本机配置的结果：`/Users/jamie/Library/Rime/build/rime_ice.schema.yaml` 含雾凇全拼及多条纠错规则；本地源方案注释明确提示部分纠错规则与全拼、简拼混输可能冲突。小鹤双拼的已部署配置也存在，且主翻译器同样引用 `rime_ice` 词典。这些是文件层证据，未确认当前前台会话所用方案，也没有实机复现用户问题；不能由“规则存在”推导“纠错效果已经满足要求”。

当前保持全拼基线，不为这一低频问题调整配置或引入语法模型。此前提出的样例分析和语法模型评估方向仅留档，不作为当前待办；上游说明模型效果也不保证在所有情况下提升。[雾凇语法模型说明](https://github.com/iDvel/rime-ice#常见问题)

双拼作为减少按键、改善输入节奏的可选试用方向，不作为修复词库管理或组句问题的前提，也不据此修改 D-03、D-07 的全拼基线。尚未决定采用哪套双拼、训练计划或双拼特有的切换上屏行为。
